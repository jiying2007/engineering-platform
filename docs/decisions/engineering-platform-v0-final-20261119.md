# Engineering Platform V0｜个人与小团队开发终版收敛方案

**版本：Final 1.1（业务需求入口修订）｜日期：2026-11-19｜适用：1–8 名可信开发者，飞书项目/TAPD + Ubuntu/Linux + Git + 既有 AI CLI**  
**文件性质：最终技术决策与落地验收基线；不代表实际主机部署、模型账号资格或业务交付已完成。**

## 1. 一页结论

**最终决定：不再建设通用 Agent／工程任务平台。** `eng V0` 仅作为**可选的、一次性、前台、本地工程执行辅助工具**；它复用既有 AI CLI、Git、原项目检查及 GitHub/GitLab。**需求与缺陷的业务权威是飞书项目或 TAPD（可经企业微信进入）；GitHub/GitLab Issue 不作为默认需求入口，也不复制业务工单。**个人开发优先使用原生 CLI；确实需要独立工作区和可复查结果时才调用 `eng`。`codex-tui` 独立负责 Codex 会话观察、待处理路由与 Git/Forge 上下文，不依赖 `eng`，也不由 `eng` 接管其会话。

**四个硬边界：**

1. **业务需求与技术交付分权。** 飞书项目／TAPD 持有需求、缺陷、负责人、版本、测试验证和业务状态；Git 持有代码与 worktree；GitHub/GitLab 持有代码分支、PR/MR、审查和 CI；AI CLI 持有模型／会话。`eng` 仅记录一次本地执行的可观测结果，不创建第二个需求/缺陷账本。
2. **不把本地检查通过等同工单验收完成。** Runner 退出码 0、`doctor` Ready 或 CI 绿色，都不能代替真实模型运行、代码语义验收、设备测试和正式交付。
3. **工单引用不等于工单内容。** 首版只消费开发者从飞书项目／TAPD 已授权取得的任务正文、验收条件及原工单标识/链接。仅输入 URL/编号不能假装已读取受权限保护的需求；不自动读写或改变工单状态。
4. **无实际收益则停止开发 `eng`。** 与原生 CLI + Git + 既有 ADK 的直接流程相比，真实任务没有减少准备、定位、留证据或失败恢复负担时，只保留必要的 Git/结果辅助功能；不再为证明平台价值而扩建。

**当前准入决定：PR #311 暂不认定为生产就绪。** 已有 Ubuntu 无模型测试及原仓 CI 证据，但关键进程归属、跨实例互斥和真实已授权模型任务尚未达到验收条件。优先修正确性，不继续叠加 UI、队列或 Provider 平台。

本方案以仓库实际代码和既有两份 2026-11-18 设计文档为依据。早期“Go + SQLite + 可选 serve”的方案是历史设计；本次最终决定明确**取代其日常架构选择**，但继承其安全、诚实状态与真实任务验收原则。未经实施和测试的能力不作为当前事实。

## 3. 最小产品形态与团队协作

### 3.1 日常路径：先用现有工具

- **个人默认**：进入项目 Git 仓库，直接使用已经登录、费用明确且被批准的 AI CLI，沿用现有 ADK、项目脚本和 Git 工作流。
- **按需 V0**：只有当一次任务需要自动创建隔离 worktree、冻结起点、保存真实检查／diff／日志时，执行 `eng run`。不允许同时由 TUI、原生 CLI 和 `eng` 各自拥有同一任务的执行生命周期。
- **Codex 场景**：如用户本来使用 Codex，可用 `codex-tui` 观察会话／待处理、审查 Git/Forge；不能把它和 `eng` 变成两层队列。此项目的 Codex/ChatGPT Work 额度限制继续生效，本次落地验证不得偷偷消耗该额度。

### 3.2 实际产研闭环：飞书项目／TAPD → 开发 → 复测

| 阶段 | 入口／负责角色 | 唯一权威与实际交付 |
|---|---|---|
| 提交、分派 | 产品或测试；**飞书项目／TAPD** | 原需求/缺陷工作项及其编号、正文、附件、验收标准、优先级、负责人；企业微信仅是进入 TAPD 的协作渠道时不单独作为第二套工单库 |
| 领取与澄清 | 研发人员在原工作项上核对范围 | 材料不足、复现不清、验收不清时先在原系统澄清，不让 AI 自行猜测，也不新建 GitHub Issue 代替 |
| 实现与检查 | 原生已授权 AI CLI，或可选 `eng` | 原代码仓库、独立分支/worktree、结果提交、真实测试命令与日志；不复制业务状态 |
| 代码审查与 CI | GitHub／GitLab | PR/MR、精确 commit、CI 和评审结果；PR/MR 描述注明原始飞书项目／TAPD 工单 ID/链接 |
| 产品验收／QA 复测 | 产品和测试返回**原工作项** | 回填代码/PR 链接、版本、测试/复现结果；**由有权限的责任人在原系统完成状态流转与关闭**，代码合并不自动关闭业务缺陷 |

一个业务工作项只认一个来源（飞书项目**或**TAPD），不得为满足开发流程在 GitHub/GitLab 再造一份同名需求/缺陷。若客户两套系统并行，也只保留上游指定的主工单身份，另一系统的关联关系按原组织流程处理；V0 不同步工单、更改责任人或版本。

### 3.3 V0 可交付的默认命令

```bash
# 首次明确选择已获准、已安装的 Runner（示意命令，不证明其登录或模型合法）
eng use -- APPROVED_CLI [ARGS]

cd /path/to/existing-git-repo
eng doctor
eng run --task /path/to/approved-ticket.md --check 'python3 -m unittest'
eng status
# 大文本或敏感任务改用：eng run --task /path/to/task.md --check 'make test'
```

`approved-ticket.md` 只是一次性开发输入，不是另一套工单：从已授权的飞书项目／TAPD 工作项提取「系统、原始工作项 ID、原始链接、问题/需求、复现或范围、期望结果、验收条件、相关附件的可用本地路径」，必要时注明保密范围。不能假定 V0 仅凭工单 URL 就能绕过企业权限读取附件，也不要求开发者每次填写治理 JSON。短而非敏感的需求仍可使用 `eng run '任务正文'`。PR/MR 提交说明关联原工单，但不自动创建 GitHub Issue。

前台默认、无定时监控、不自动重试、不自动 push/PR/合并、不自动刷写硬件。`doctor` 不调用模型，不得把“Runner 路径存在”写成“模型登录可用”。大任务和敏感任务使用受权限控制的文件；短文本可能进入 Shell 历史和进程参数。

### 3.4 团队使用的边界

| 场景 | 支持决定 | 权威与隔离 |
|---|---|---|
| 单人、多仓库 | V0 可按需使用；一个任务一个仓库 | 各项目 Git，开发者自己的 Runner |
| 2–8 人、各自开发机/账号 | **目标场景**；通过 PR/MR、CI 和仓库规范协作 | 各自本地状态、独立凭据；**业务事实在飞书项目/TAPD，代码事实在 Git/Forge** |
| 多人共用一个 Ubuntu 主机 | 仅在独立 OS 账号、仓库与权限边界明确时使用 | 不共享模型 token，不声称同 UID 互相隔离 |
| 同一 Git common-dir 多实例 | **P0 修复前禁止并发** | 由 Git common-dir 拥有一致互斥与恢复状态 |
| 共享团队队列/跨主机调度 | **不属于 V0** | 先复用现有 SSH/tmux/Forge；确有需求再独立立项 |

工单验收与测试由飞书项目／TAPD 负责，开发约束保存在 `AGENTS.md`、原 CLI 配置、项目脚本和 CI；不新增团队服务、RBAC、共享任务账本、跨 Agent 调度或重复 Skill 平台。

### 3.5 工单集成的取舍：默认零接入

首版不新增飞书项目／TAPD API 客户端、Webhook、定时同步、机器人授权系统或双向状态机。理由是两种企业系统都涉及真实组织权限、字段映射、测试流程及附件访问；没有实际账号与样例时提前开发适配器只会复制一个业务权威。开发者人工复制/导出已授权任务文本作为起点，产出真实提交/PR/MR 后回填原工单即可完成最小闭环。

若实际试用证明人工搬运是主要负担，第二阶段**只选择正在使用且获授权的一套来源系统**，先做工作项**单次、只读、按 ID/URL 获取**，核对字段与附件权限后供用户确认；不默认自动同步状态。若以后要回填，仅在现有 API 及权限经过真实验证后，允许显式写入准确 PR/commit 引用，并核对操作回执。当前没有已验证可调用的飞书项目／TAPD 连接器，不作“已接入”承诺。

## 4. 代码复审：必须修正的问题

### P0-A：跨实例仓库互斥与执行权归属

当前 V0 锁位于各自 `ENG_HOME/locks` 下；更换 `ENG_HOME` 可能绕过同一 Git 仓库的互斥。需以规范化 Git **common-dir** 为唯一仓库身份，并把仓库级锁放到相同的可验证位置（或使用等效单主机所有者），跨状态目录、worktree 别名均不能绕过。旧执行器与 V0 共存时不能假定互斥协议兼容；先实地停止旧执行器或显式阻断混用。

**验收用例**：同一 Git common-dir、不同 `ENG_HOME` 的并发请求，第二个必须拒绝且不启动 Runner；不同独立 clone 可各自执行；运行期间失联不应导致未证实停止的工作区被复用。

### P0-B：异常退出后的执行身份与不盲重试

现有脚本能响应常规信号，但监督进程被 `SIGKILL`、系统崩溃或进程启动握手中断后，只有临时 flock 和简要 JSON 不足以证明旧子进程已停止。应在启动前**持久记录 launch intent**，在可观测启动时绑定 PID/PGID、Linux `/proc` 启动时间、boot ID 或等价可验证 OS 身份；后续启动先核实原身份和工作区。无法证明停止时标记 `unknown` 并拒绝再次执行，直到人工核对。允许只做小规模 Linux 专属实现，不建设恢复服务或可重播任务系统。

**验收用例**：在启动前、启动后、写回身份前和运行中注入强制杀死监督进程；验证不自动开启第二个 Runner、改动与日志留存、状态不会由未知变成功；若子进程脱离进程组，则不能宣称已全部停止，需依现有 OS cgroup/受管进程边界处理或拒绝该 Runtime。

### P0-C：Git 暂存与敏感产物边界

当前候选会在有限敏感文件名检查后执行 `git add -A`。这无法保证陌生名称的凭据、构建产物及大目录不会进入同仓库共享 Git Object Store。建议默认自动暂存**已跟踪文件的修改**；新文件通过明确的路径预览/允许清单纳入，拒绝符号链接逃逸、特殊文件、疑似凭据和超限内容，且**从不自动推送**。Git filter 不仅核查局部配置，还须覆盖实际生效的 include/config 来源；不能证明安全时拒绝执行。

**验收用例**：生成新源码、未知名密钥、构建目录、符号链接以及可执行 smudge/clean/process filter；仅经允许的新源码进入本地提交，危险文件只保留工作区供人工判断。

### P1：首次使用及真实能力探测

- `doctor` 应核对 Git、Python、数据目录权限、明确选定的 Runner 实际可执行文件以及项目检查程序是否存在；不探测模型账号密码、不静默发送测试 Prompt、不声称额度可用。
- `eng use` 的“禁用 Codex 名称”不是不可绕过的模型额度控制，Shell 包装器可能绕过名字匹配。应以用户批准的**具体执行命令、目标 Provider/费用来源和实际运行记录**作为准入事实；没有这份事实时保持禁用真实模型调用，不发明复杂凭据平台。
- 明确状态语义：`locally_verified` 只表示当前提交的全部配置检查实际通过；没有检查、检查改动源码、只有分析没有提交、设备未测时必须列出待办；Usage 未观察到就是 `unknown`，不是 0。
- 保护日志和结果存储；任何自动删除仅限已确认停止、已保存结果的工具自有目录。初版不需要复杂清理调度。

**未列出的功能暂不纳入**：TUI 面板、Web、共享队列、自动模型切换、自动修复循环、统一 Provider SDK、多租户、自动发布/合并、完整对话存储、独立知识库。

## 5. 最短实施顺序和退出门槛

| 阶段 | 必须有的可核验结果 | 放行判断 |
|---|---|---|
| G0 冻结范围（已确认） | 本文件作为唯一最终方案；PR #311 仍是候选，不暗示已部署 | 不继续添加新功能 |
| G1 可靠性修复（未完成） | P0-A/B/C 的可复现负例、修复、原有 no-model 测试、Ubuntu 发行包与精确 SHA CI | 任一进程未知／越权暂存仍在 → 不得放行 |
| G2 个人真实使用（未完成） | 在**实际 Ubuntu 主机**安装；一个已批准 Runtime 从**真实飞书项目或 TAPD 已授权工作项**完成代码修改、结果提交、测试日志、原工单引用、运行费用来源及停止语义核对 | 不准用合成 Runner 代替真实 AI 编码 |
| G3 小团队验证（未完成） | 两个实际研发仓库、约五个由飞书项目／TAPD 原工作项驱动的低风险任务，包含缺陷修复、需求功能、材料不足澄清和中断恢复；由产品/QA 在原系统参与复测，团队场景两名开发成员各自账号操作 | 记录真实人工步骤、执行时间和问题，不强制团队服务器 |
| G4 收敛去留（待决） | 将同类任务的原生 CLI + Git 与 eng 路线进行实际对比，统计从原工单领取到 PR/MR/回填的准备步骤、失败定位与恢复、调用次数/可见成本 | 没有明确净收益 → 停止执行包装、仅留辅助功能 |
| G5 旧系统退出（未完成） | 旧主机停机与 UNKNOWN 清单、旧 DB/日志及必要 GitHub Actions 制品归档、仓库/Issue 身份保留、受保护 PR 删除旧 Core/Go/CI | 未证实安全停止 → 不删运行资料；不保留长期兼容层 |

**关键停止规则**：无已授权 Runtime 时，G2/G3 显示阻塞，不继续无模型准备循环。G1 可使用确定性 Linux/Git 测试而不耗费模型额度。任何阶段未通过，不自动推高“已落地”状态。一次批次只修真实阻塞问题；若连续增加流程而不能完成新的研发任务，停止扩建。

## 6. codex-tui 的借鉴边界

吸收 `codex-tui` ADR-012、ADR-004 和首次部署原则：产品个人优先、上游负责执行、Git/Forge 负责**代码交付**事实、飞书项目/TAPD 负责**业务工单**事实；局部状态仅作操作视图，不复制队列或 Agent 协议。实际采用中允许 `codex-tui` 独立可选存在，但**eng 无需依赖 codex-tui、也不复刻其 Registry、Board、Terminal Drawer、远程连接、审批和发布界面**。

特别注意：`codex-tui` 自身仍把 v1.4 Stable 的真实部署资格与 CI 绿色明确区分；因此只能借鉴设计与验证方法，不能用其历史计划替代 eng 的真实执行证明。

## 7. 归档、迁移与最终关闭

**单一方案权威**：本 Markdown 保存在 `engineering-platform/docs/decisions/engineering-platform-v0-final-20261119.md`。DOCX 仅作离线阅读快照；后续实施以仓库受保护主线版本为准。不要平行维护不同结论的多份“终版方案”。

**现有仓库处置**：完成 G1–G4 才切换日常入口；在主机逐个确认旧执行进程、UNKNOWN 外部结果、旧 DB、制品与备份后，另用清晰的受保护 PR 删除旧 Core、Go `tool/` 和过时 CI。已知历史缺陷应标记“被新范围替代／历史保留”，不能标记“已修复”。Git 历史与离线证据按原身份保留。

**`digital-worker` 退役**：历史 Git bundle、原仓 GitHub Issues/PR 导出已验证可恢复（仅历史研发平台记录，**不是产品和 QA 的飞书项目/TAPD 工单备份**），但 GitHub 仓库目前尚存在且部分原始 Actions 制品未全量保全。需核对要保留的未过期制品和真实主机，再使用有删除权限的 GitHub 账号永久删除；事后通过精确仓库 404 / API 不可达确认。当前 GitHub 连接器未提供仓库管理删除动作，不能把“提供脚本”写成“已删除”。
