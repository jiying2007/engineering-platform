# Engineering Platform｜结合 Codex CLI 实际使用历史的最终研发方案

**版本：Final 1.2（Codex CLI 实战融合）**　　**日期：2026-11-19**  
**适用范围：个人主用、2–8 名可信研发成员；Windows Terminal → SSH → Ubuntu；多 GitHub/GitLab 仓库；飞书项目/TAPD 工单；现有 ADK Skills。**  
**决策性质：唯一维护的研发工作流与工程工具收敛方案，不是对 AiotServer01、模型凭据或产品交付已完成的声明。**

## 1. 最终决定（一页读完）

**不再建设统一 Agent/工程任务平台。以既有 Codex CLI 和项目工具为主；保留 codex-tui 的独立会话工作台定位；eng 只有在真实减少 Git worktree 和证据整理工作时才保留。**

1. **交互式编码优先原生 Codex CLI**：开发者在实际 Ubuntu Git 仓库中使用现有 Codex、Claude Code 或已经批准的其他 CLI；继续复用 ADK Skills、AGENTS.md、项目脚本。不要让 eng 包装、托管或复制原生会话/审批/恢复语义。
2. **codex-tui 只做 Codex 会话观察与人工控制**：多仓会话定位、Needs You/Working/Ready、查看 Git/Forge；不成为 eng 或业务工单管理系统，也不取得第二份 Agent 执行权。
3. **eng 定位为可选的确定性辅助**：仅当用户明确需要隔离 Git worktree、留存实际检查命令、diff、日志和准确提交时使用。默认不调用模型、不自动复跑、不发布、不接管会话。不用 eng 并不影响正常研发。
4. **业务需求/测试缺陷在飞书项目或 TAPD**：产品/QA 创建、分派和验收，企业微信可作为 TAPD 入口；GitHub/GitLab 负责代码、PR/MR、评审和 CI，不能再默认复制一份业务 Issue。研究和内部工程任务仍可由实验清单、仓库技术记录管理，不强制进入产品工单。
5. **KWS/Audio、固件/FOC/OTA 仍走各自实际执行链**：KWS/Audio 使用现有数据—训练—评估事件驱动流程；硬件/固件需真实工具链、目标板和 QA/供应商实测。eng 不建设科研调度器或硬件验证平台。
6. **当前额度禁令不变**：禁止消耗 Codex CLI/ChatGPT Work 共享额度。`codex --version`、`codex --help`、`codex login status` 等只读检查可以作为无模型预检；任何新模型回合必须先有被批准且实际可用的费用/凭据执行通道，并在启动前确认授权。CLI 名字不是费用来源；不能通过包装器、别名或中转站绕过禁令。

**单一权威：飞书项目/TAPD 管业务；Codex/其他已批准 CLI 管模型及会话；Git 管代码/worktree；GitLab/GitHub 管 PR、CI；算法流水线管理实验；eng 仅管其可选、可观测的一次辅助动作。**

## 2. 已发生的 Codex CLI 使用历史：为何不应该重造执行器

| 历史时期 | 可核对的经历 | 对方案的约束 |
|---|---|---|
| 2026-05 | AiotServer01 上 Codex CLI 0.130.0，Device Code/OAuth 登录曾失败；网络可达不等于登录成功 | `doctor` 要区分二进制存在、登录状态、模型可用及费用准入，不得把其一替代其他 |
| 2026-07 | 清理 npm 残留、切换官方 standalone Codex 0.146.0，曾遭遇 Bash 缓存旧命令路径 | 安装只维持一条首选路径；升级后用 `type -a codex`、`hash -r` 和 `codex --version` 排查。团队不强制统一精确版本 |
| 2026-09-21 | 存在 Codex CLI 0.146.0 与 Claude Code 的真实执行完成证据；部分领域验收被错误的固定 `tests/` 路径阻塞 | 不需要重新证明“原生 CLI 能运行”；验收命令必须来自各项目真实 scripts、artifacts、SHA256SUMS，而不是中央平台假定目录 |
| 2026-09-27–29 | AiotServer01 Ubuntu 22.04.5：Codex CLI 0.157.1、ChatGPT 登录、gh 登录已实际出现；明确允许个人考虑中转站，团队版本不必一致 | 采用 Provider/Credential/Execution 三维记录：费用来源、登录身份、CLI 能力独立核实；未经过资格验证的 Relay 不视为可用 |
| 2026-11-04 | codex-tui 1.4 候选曾在 Ubuntu 连接 Codex App Server、观察 55 个本地会话，并完成部分真实 SSH/TTY 交互测试；正式 Stable 资格仍未确认 | 可复用现有多会话定位价值；不把 TUI 候选与所有实际生产资格画等号，不创建另一个 Session/Queue 权威 |
| 2026-10 以来的现行要求 | 禁止消耗 Codex/ChatGPT Work 共享额度，优先已有 Dot、GitHub Actions、GitHub 插件及开源执行环境 | 历史 ChatGPT 登录方式只是事实，不是现在可以发起模型调用的授权；任何验证不准偷用额度 |

**历史事实的边界**：这些记录证明曾经安装、登录、执行和观察；不能推导出当前同一二进制版本、身份状态、Relay 合同、余额、模型能力或硬件业务验收仍有效。不要为满足资格门禁安装多个固定版本或复制 `auth.json` 到仓库/共享账号。

## 3. 推荐的工作流：默认原生，按需辅助

### 3.1 日常编码：Windows SSH 登录 Ubuntu，执行权只属于原生 CLI

**正常使用（需要已批准的模型渠道才能发起执行）**：打开 Windows Terminal，SSH 到目标 Ubuntu 主机，进入**实际代码仓库**；用 `git status` 确认分支与未提交内容；以当前工作树运行经过授权的原生 Codex CLI，按项目 AGENTS.md、ADK Skills、构建脚本进行工作。需要同时观察多个 Codex 会话时，单独启动 codex-tui，它只操作同一实际 Codex 环境的可观测会话。

**无模型只读预检（当前即可执行，不自动调用模型）**：

```bash
# 在实际 Ubuntu 执行，不要把 Windows 的路径当作服务器路径
type -a codex
codex --version
codex login status
codex exec --help
# 如果 shell 还命中已卸载的旧路径，再运行 hash -r 后重新核对
# 在目标源码目录执行：
git status --short --branch
git rev-parse --show-toplevel
# 使用 GitHub 或 GitLab 的人员再检查各自的 gh/glab 登录
```

这里的 `codex login status` 只能说明 CLI 观察到的本地身份状态，不代表现在的计费渠道已批准，也不保证发起模型回合会成功。**当前不执行 `codex` 交互提示或 `codex exec` 模型任务。**

**获得单独授权之后**：人工作业直接使用 `codex`；有实际批处理需求时才使用官方 `codex exec`，且由实际命令版本的 `--help` 核实可用参数。优先利用原生权限、沙盒、会话、输出与停止能力，不再增加第二层 eng Runner/Resume/Queue。`tmux` 只能让终端会话继续存在，不代表模型执行永远成功或具备断电恢复。

### 3.2 两类费用/登录通道：允许做能力检查，不自动选择

| 通道 | 历史与现状 | 实际准入规则 |
|---|---|---|
| **A. ChatGPT 登录的 Codex CLI** | 过去在 AiotServer01 上使用过，曾完成模型执行 | 目前受 Codex/Work 额度禁令限制：**禁用新的模型回合**。CLI 可以保留，做只读预检。解除额度禁令以前不得当作自动化默认来源 |
| **B. 独立计费的 Relay/其他凭据** | 用户曾明确提出个人可使用中转站；没有提供已通过的当下真实合同和一轮现行目标任务 | 必须先确认提供商、endpoint、模型映射、登录方式、计费主体、可用预算、内容保留/隐私、工具/沙盒支持、错误/超时语义；在 **明确获准** 后以专用配置验证一次真实任务。绝不自动从 A 降级到 B 或相反 |
| **C. 项目 GitHub Actions/科研算力** | KWS/Audio 原仓库已存在数据、训练、评估工作流 | 只用于其原本项目级工作流，按既有预算/准入执行，不借 eng 调度器兜底，也不使用 Codex/Work 共享额度 |

不把账号登录方式、Provider、模型和执行方式混为一谈；团队各人可保持自己的版本和认证。只需记录实际可执行文件路径、版本、必要能力、所用通道代号与预算批准证据，**不保存密钥本身**。不要引入 OPENAI_ADMIN_KEY、WIF、泛化 Provider 控制面，除非未来有经过批准的真实企业部署需求。

### 3.3 产品和 QA 工单：飞书项目/TAPD 是唯一业务入口

1. 产品/测试在飞书项目或 TAPD 提交需求或 Bug，带来源系统、ID、原链接、相关日志/附件、复现条件、版本和验收标准；企业微信可作为访问入口。
2. 研发人员在原工单领取、澄清和确定范围；未取得业务系统授权的自动化不应凭一个 URL 假装读取私有附件。敏感材料只保存到受控位置，尽量引用可访问的原文件，而不是复制到公开 PR。
3. 已批准的原生 AI CLI 实现代码，执行对应项目真实构建/测试；记录准确 commit、相关硬件版本、已验证/未验证项目。按需用 Git worktree 或可选 eng 辅助整理证据。
4. 在 GitHub/GitLab 建 PR/MR 并关联原始工单 ID/URL（仅在权限和保密规则允许时）。Git 负责代码、Forge 负责审查 CI；产品/QA 返回原飞书/TAPD 工单复测、关联版本/日志并作业务关闭。**PR 合并不自动等于 Bug 关闭。**

GitHub/GitLab Issues 可用于**仓库内部技术维护**，不是产品、测试正式工单的镜像。跨两个业务系统时先指定一个上游原工单；不开第二套双向状态同步服务。

### 3.4 算法/硬件和工程工具：分别延续成熟原链

| 工作类别 | 执行位置和事实权威 | 交付或验收边界 |
|---|---|---|
| KWS 端侧英文/中文模型、TTS/三 ASR、数据准入、训练、FAR 与资源评估 | kws-data / kws-pipeline 的现有事件驱动工作流与合格执行节点 | 复用已核验数据；训练/开发/校准/锁定测试及声源组隔离真实可查。`eng` 不调度训练，不创建小时巡检 |
| Audio/AEC/NS 等连续实验 | audio-pipeline 原仓数据、实验、独立来源评价及 CI | 只按真实候选、声学数据和独立评价闭环；CI 绿色不等于 DSP 算法质量提升 |
| PCR02/SSC305/Linux、GD32L235/MM32SPIN023C、FOC/OTA/充电桩 | 原生 CLI + 原生构建工具链 + 设备/供应商/QA 测试 | 保留芯片/硬件版本、固件 SHA、升级/回退结果、电流/温度/实机日志；没有设备时明确待硬件验证 |
| agent-dev-kit / Skills / codex-review-service / safe 系列 | 对应仓库、现有自测和 PR/MR/CI；审查服务继续用自身部署 | 不经 eng 新建管理服务或复制一套自动审查/发布引擎 |
| 技术调研、ODM 成本选型、供应商和管理工作 | 现有文档/会议/飞书/TAPD/企业协作 | 交付文档、决策、变更通知，不强制生成 Git 任务或模型执行 |

## 4. eng V0 最终去留：先做价值判断，而非继续扩建

**当前 PR #311 不能直接作为默认生产工具合并。** 它引入了另一层运行器，并按名称禁止 `codex`，这与用户真实 Codex CLI 主路径冲突；它推荐的 OpenCode 示例也尚未在用户机器上通过资格验证。名称级黑名单无法区分使用 ChatGPT 共享额度和使用真正独立、获准的计费通道，不能充当真实成本边界。

**首选最小产品形态**：不拥有模型调用、会话、队列、通知或工单；只在需要时辅助 Git worktree 创建/验证、运行现有本地测试、整理 diff/日志/结果。日常不要求安装 eng；**能从 Codex CLI + Git 直接完成的任务，绝不强制经过 eng**。用户不应因为使用工具而新增第二份 task ID、状态账本或手工回执。

若坚持保留 PR #311 的“前台模型包装”分支，准入前必须先补 3 个 P0：

- **跨实例互斥**：锁的身份与位置绑定同一 Git common-dir，不因不同 `ENG_HOME`、worktree 或别名绕过；不和旧执行器混用时假定安全。
- **进程与崩溃恢复**：启动意图先落盘，PID/PGID + 启动时间/boot ID 等身份有可核验记录；异常退出无法确认旧进程停止时拒绝再启动，不盲目重放模型。
- **敏感代码和产物**：不得在不充分检查时对全部未跟踪文件直接 `git add -A`，只暂存已跟踪变更及经明确允许的新增源码；输出保存在本地私有目录，不自动推送。

这些修复会增加维护成本，必须与直接用 CLI 的收益比较。**若没有可测收益，关闭包装型 PR，缩减或移除该执行包装，不因为已经写好代码而继续投入。** 现有 Go/SQLite `tool/`、旧多服务 Core 和旧 CI 属于待退出历史，不作为新用户日常安装和测试前提。

## 5. 最短实际落地顺序和验收（不增加定时任务）

| 关口 | 真实通过条件 | 没有证据时的结论 |
|---|---|---|
| G0｜工具和主机清点 | 在 AiotServer01/各开发机明确 `codex` 可执行路径/版本、`codex login status`、Git/gh/glab、SSH/TUI 终端和实际项目工具链；不使用模型 | 仅“已完成预检”，不宣称可实际调用模型 |
| G1｜费用与权限 | 按 A/B/C 中**明确一条**已获准的通道确认身份、模型、权限、预算、隐私、沙盒及停止语义；禁用默认 fallback | 无获准通道 → 模型研发验证保持阻塞；允许无模型代码与文档工作 |
| G2｜个人真实编码 | 从真实飞书/TAPD Bug 和一项真实工程维护任务中选低风险工作，在已批准通道下完成原生 CLI 修改、真实检查、diff、commit/PR、原工单回填；不以历史 fixture 代替 | 不能用 PR/CI 成功替代原工单、真机或模型资格 |
| G3｜2–8 人团队复用 | 两个实际研发仓库、约五个任务，覆盖功能/缺陷、一次失败恢复以及有硬件限制的正确标注；两名开发者各自账号、Git PR、业务系统验收 | 仍不可据无模型 CI 宣称多人协作已上线 |
| G4｜eng 价值裁决 | 对比直接 Codex/批准 CLI + Git 与额外 eng 路径：步骤数、准备时间、查日志/恢复时间、实际检查证据和可见调用成本 | 无清晰净收益 → 不合并包装型 eng，最多保留纯 Git/证据辅助 |
| G5｜旧平台退出 | 保全旧 Git/Issue/PR、必要 Actions 制品/主机日志；核实未知远端副作用与旧进程停止，受保护 PR 精简旧 Core/Go CI；数字仓库删除后再核验 404 | 主机未清、历史未保全或无 GitHub 管理删除通道 → 不宣称完成退出 |

**最重要的止损标准**：真实开发不能持续完成时，先修实际模型执行资格或项目工具链，而不是继续堆 `eng`、Work/Queue、审核规则、Scheduled 巡检、统一 Provider、知识库或漂亮的状态页面。

## 6. 各工具唯一负责什么

| 工具/系统 | 唯一责任 | 明确不做 |
|---|---|---|
| 飞书项目 / TAPD | 产品/测试工作项、优先级、版本、验收和 QA 关闭 | 不成为代码仓库、自动生成第二份 GitHub Issue |
| Codex CLI / 已批准的其他 CLI | 模型对话、代码修改、会话/审批/执行生命周期 | 不成为业务工单权威；无额度授权时禁止模型回合 |
| codex-tui | 观察/跳转 Codex 会话、待处理、Git/Forge 上下文 | 不拥有第二套 Agent/Queue/Provider/工作流服务，不保证未连接目标的实时状态 |
| Git + gh/glab + GitHub/GitLab | 源码、分支、worktree、PR/MR、审查与 CI | 不代替 QA 复测、设备测试或科研模型评价 |
| ADK Skills、各仓库脚本 | 方法、规范、构建/测试和可复用经验 | 不再复制 Skill 注册/执行平台 |
| KWS/Audio 原科研流水线 | 原数据/模型/实验、事件驱动训练与质量评价 | 不让 eng 做训练任务中心 |
| eng（如确有收益） | 可选、低成本、确定性的 Git/worktree/结果辅助 | 不创建新任务主权、不发起未经准入的模型、不做队列、服务或自动发布 |
